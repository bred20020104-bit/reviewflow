# ReviewFlow 系统设计

日期：2026-11-02。状态：依据已讨论方案整理；实现前由用户确认阶段计划。

## 意图与约束

面向开发完成、准备上线的小型 Python 项目，帮助用户发现、验证问题并提出可审计的修复。默认输入为本地仓库/目录，不要求复制代码或提供 `base/head`。变更审查是后续扩展，不是默认入口。

课程要求工作系统、明确角色/工具/任务分工/通信/最终决策，强调有意义的多 Agent 协作而非独立调用的拼接。提交源代码、运行说明、最多 10 分钟视频、Slides 和个人贡献说明，截止 2026-11-23 23:59；以 Canvas 最终要求为准。

系统不是生产上线认证、全语言安全审计平台或自动部署工具。成功标准是可复现、可解释、范围清晰的代表性案例，不是承诺找出所有问题。

## 已确定的产品决定

- Python >= 3.11；本地开发优先 Python 3.12。
- LangGraph 负责编排；自行设计业务协议、证据规则、审批与权限。
- 五个 Agent：Supervisor / Planner、Correctness Reviewer、Security Reviewer、Verifier、Patch Agent。
- Planner 兼任语义层 Main Agent，不另建一个无明确职责的主 Agent。
- 确定性模块控制读写权限、状态转换、工具执行、报告、Git、预算与重试上限。
- 先报告再修复，修复、commit、push 分开授权；不自动合并。
- 独立 worktree 承载 Git 修复，原工作区保持不变。
- 先 CLI 和可测试服务，后 Streamlit；首版不做 React/FastAPI 分离部署。
- 先小型 Python 项目、正确性与安全问题；不做无限辩论、IDE 插件、多语言支持或自动依赖安装。

## 尚待接入阶段确认的选择

模型提供方、具体模型标识、API 预算尚未选择。引入真实模型前确认代码上传范围和费用；基线和多 Agent 对比固定模型及工具权限。项目不依赖某个编码助手的登录状态作为 API 凭据。

确切的沙箱镜像和允许的目标测试命令，在工具执行阶段确定并固定版本。当前只有本地 Python 3.12 可用这一事实得到检查，Docker 尚未验证。

界面细节、任务并发数、提示词措辞可由实现者在测试和预算约束内决定。不得自行改变审批与发布边界。

## 输入与快照

### Git 项目

默认固定当前已提交的 `HEAD`，记录 commit SHA、分支（或 detached HEAD）和清单。未提交/暂存/未跟踪内容不自动包含；存在这些内容时向用户明确提示，只读检查，不 stash、不提交、不丢弃。

首版可以提供显式目录快照模式查看当前文件，但此模式不进入自动 Git 修复流程。Git 修复只接受有明确基准提交的 HEAD 快照。

### 普通目录

允许只读扫描和审查，通过文件内容哈希标识快照；不自动初始化 Git，不提供自动提交/推送。可输出人工修复建议。

### 上下文与覆盖

枚举文件、识别模块、建立 Python 符号/文本索引，按任务获取函数、调用方、测试、需求。不把仓库所有文件复制给所有 Agent，不要求向量数据库。

目录过滤、文件大小、文件数量和总文本量必须有显式限制，报告每个跳过项及原因。超过预算时不能声称完成全仓库审查。具体首阶段默认值见独立规格。

扫描覆盖、语义审查覆盖和执行测试覆盖分别记录。文件被索引不代表被审查；模块完成约定任务不代表不存在缺陷。

## 角色与工具边界

| 角色 | 输入与工具 | 输出与限制 |
| --- | --- | --- |
| Supervisor / Planner | 项目清单、符号概况、需求、任务状态；只读检索 | 模块/调用链任务、优先级、补充信息需求；不能绕过审批 |
| Correctness Reviewer | 任务、相关代码、调用点、测试、只读工具 | 有触发条件和具体影响的候选问题；首轮不读取其他 Reviewer 的结论 |
| Security Reviewer | 任务、代码、输入来源、权限边界、静态工具结果 | 有数据流和可达性依据的安全候选问题；工具告警不是结论 |
| Verifier | 候选问题、需求、源码、受限验证工具 | accepted/rejected/unresolved、反证和证据类型；补丁验证时用新上下文，不沿用修复者的自我论证 |
| Patch Agent | 用户选择的问题、相关快照、失败反馈 | 最小补丁与解释；不弱化测试、不改需求、不做无关重构 |

静态检查、测试和 Git 由工具层执行；模型输出不能伪造工具的退出码和日志。Git Workspace Manager 是普通程序模块，不是第六个自由操作 shell 的 Agent。

## 协议与共享状态

采用校验后的结构化对象，不使用无限自由群聊。阶段二使用 Pydantic 定义持久化 schema。

- `RepositorySnapshot`：输入模式、基准提交或内容摘要、相对路径清单、过滤/限制结果。
- `ReviewTask`：任务 ID、角色、相关路径/符号、目标、预算、任务状态。
- `Finding`：问题 ID、任务 ID、位置、根因、触发条件、影响、严重性、证据引用、判定状态。
- `Evidence`：快照 ID、类型、文件/行号或工具调用 ID、可供审阅的摘要。
- `VerificationResult`：accepted/rejected/unresolved、理由、证据引用；动态复现另用独立字段记录。
- `PatchProposal`：基准快照、选中问题 ID、diff、补丁哈希、影响范围。
- `Approval`：操作类型、任务、基准快照、补丁/提交哈希、目标分支/remote（适用时）、明确的用户动作。
- `ToolRun`：受控工具标识、执行版本、退出码、超时/阻塞状态、脱敏日志、耗时。
- `ReviewState`：上述记录、阶段、费用/调用计数、待解决冲突、事件日志。

不持久化内部推理链；记录简明决策依据、证据和可复现工具结果即可。修复、提交和推送的批准记录不可互换。

## 工作流与决策

1. 建立快照，报告输入范围和排除项。
2. Planner 拆分检查任务；角色首轮独立分析。
3. 合并重复根因但保留来源，Verifier 寻找反证。证据不足时最多请求一次补充；仍不足则 unresolved，不进行多数投票。
4. 可用执行环境下设计最小复现；先确认原版本因目标缺陷失败，再对同一测试验证补丁。需求不明时不能把模型生成的预期值作为唯一真值。
5. 输出审查报告并暂停。用户未选择问题和批准修复时，没有源码写入。
6. 获批后在独立修复 worktree 中生成补丁；一次只处理一个问题，按顺序形成修复链，避免并发补丁互相覆盖。每个问题最多两次补丁尝试，重试计数持久化。
7. 每个候选补丁执行目标验证、原测试回归和必要的专业定向复审；组合后的最终补丁再做一次汇总验证。失败修改不得留在下一个问题的基线上。无法修复的问题单独保留。
8. 展示最终 diff、逐项结果和未覆盖事项。只有实际通过约定验证的最终补丁才提供正常提交操作；环境阻塞或失败的补丁只允许导出为明确标注的未验证建议。
9. 用户批准具体补丁后，工具层只暂存获批修改并生成本地 commit。
10. 用户单独确认 remote、目标分支、提交集合及发布范围后，推送修复分支。远程冲突/认证失败保留本地成果，不强推。

修复失败通常只回到局部修复与验证，不重新执行整个仓库审查。需求变化、补丁范围扩大或要求迁移到新基线时，回到 Planner，重新确认范围及必要授权。

多个问题顺序修复时，中间测试使用“最后一个已验证补丁 + 当前候选补丁”的临时文件状态，不提前创建用户尚未批准的提交。最终审批绑定完整累积 diff；局部验证结果不能自动证明组合结果正确。

## Git 安全规则

- 固定基准提交，原分支/工作目录不切换；worktree 在受控目录创建，使用 `reviewfix/<run-id>` 唯一分支。
- 检查原仓库可读且所需基准存在；拒绝路径逃逸、未知工作区覆盖和不匹配的版本。
- 用户在原项目继续开发不会自动更新修复基线。报告基准落后；若要求集成新版本则重新验证，不能沿用旧审批。
- 提交前重新核对文件差异、补丁哈希和暂存区，不用无差别 `git add .`。
- 不自动 stash、清理用户文件、修改 remote、force push、推送主分支或合并。
- worktree 不是执行沙箱；仓库配置、hooks、过滤器、子模块和脚本不被默认信任。Git 工具仅允许审核过的操作，实施阶段对这些执行入口专门测试。
- 清理工作区前核对归属及用户新增文件；不能用破坏性命令处理未知内容。
- Git 凭据使用宿主机的凭据管理器，不交给模型或目标代码。

## 执行安全与失败状态

仓库注释、README、工具日志均为不可信数据，不可改变系统权限。实际读取路径限制在允许根目录，禁用对范围外软链接的跟随。

后续动态测试在非 root、默认禁网、无凭据、无 Docker socket 的受限环境中运行，限制 CPU、内存、进程数和时间。初期只执行团队审核过的样例；不声称可安全执行任意恶意仓库。

不自动运行目标的安装脚本，也不自动安装任意依赖。缺依赖标为 blocked；超时标为 timeout；未运行标为 not_run。原测试基线失败不自动归因于补丁。

执行检查区分 `passed`、`failed`、`blocked`、`timeout`、`not_run`。阶段结果不能仅由模型文本覆盖。

## 报告与界面

第一份报告：问题列表、accepted/rejected/unresolved、证据来源、覆盖清单、限制、成本和工具状态。

第二份报告：用户选中项、最终补丁、每项尝试次数、目标与回归测试、补丁复审、未解决项、基准提交与审批状态。

模板渲染结构化事实，不额外调用总结 Agent 改写判定。Streamlit 后续提供项目输入、进度摘要、证据、问题选择、diff、明确分开的修复/commit/push 操作。CLI 是独立核心接口。

## 评价与创新边界

准备约 30 个小型项目案例：10 个开发案例，20 个冻结测试案例；含无缺陷案例、人工植入和许可允许的真实缺陷。按项目/变体分组划分，避免同源变体跨集合泄漏。

比较单 Agent、多 Agent 无 Verifier、完整系统、完整系统无修复重试。固定模型、工具权限、输入和配置，报告真实 Token/耗时，必要时补充近似预算匹配比较。

按根因去重并人工核验，报告 precision/recall/F1、无缺陷误报率、Verifier 正确驳回与错误驳回、独立评估修复率、新回归、费用和覆盖限制。参考补丁、答案和隐藏测试不提供给 Agent。

多 Agent 更有效是待检验假设。贡献是机制组合、可审计实现及实验分析，不声称首次提出 Reviewer–Verifier 架构。

## 阶段划分

1. **仓库输入与覆盖报告**：独立规格和计划；离线、只读，无真实审查结论。
2. **结构化审查**：任务/问题协议、真实模型接入、LangGraph、单 Agent 基线、专业 Reviewer 与语义 Verifier；在调用前确认提供方和预算。
3. **隔离验证与修复**：执行基线、复现测试、补丁、有限重试、批准恢复、worktree、commit/push 门禁。
4. **界面与评估交付**：Streamlit、冻结实验、失败案例、录制、Slides、贡献说明。

后续阶段各自编写可执行计划，不把未决的 API 或沙箱细节伪装成已实现。
