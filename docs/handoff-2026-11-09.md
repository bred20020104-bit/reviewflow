## 5. 如何安装与使用

所有工具安装、配置和命令从可信的ReviewFlow目录执行，不在目标仓库里运行安装脚本。

### 5.1 新机器安装

```bash
cd /path/to/reviewflow
python3.12 -m venv .venv
.venv/bin/python -m pip install -e '.[dev,review]'

# 新环境创建隔离启动器；已有review时安装器拒绝覆盖，先检查现有文件
.venv/bin/python -I -m reviewflow.install --bin-dir "$PWD/.venv/bin"
.venv/bin/review --help
.venv/bin/review repair-run --help
```

当前本机已有 `.venv/bin/review`，不需要重复安装。`pip install -e`的标准入口是 `reviewflow`；推荐使用额外生成的 `review` 隔离启动器，或直接用 `.venv/bin/python -I -m reviewflow.quick ...`。

```bash
.venv/bin/pytest -q
.venv/bin/ruff check src tests
```

以上是产品自身测试，不是对真实目标仓库的验收。POSIX/macOS/Linux为当前适用环境，Windows未支持。Docker测试还需要Docker服务和已准备的可信不可变镜像，镜像中必须包含pytest和目标所需依赖；运行时不联网安装。

### 5.2 模型配置

```bash
# 已有私有配置不要覆盖
cp -n config.example.toml config.local.toml
cp -n secrets.example.toml secrets.local.toml
chmod 600 secrets.local.toml
```

只在私有文件中填写：

```toml
provider = "openai"
api_type = "responses"
model = "账户可用的模型ID"
base_url = "https://已批准的服务地址/v1"
api_key = "仅本地填写"
```

`config.local.toml`保留 `secrets_file = "secrets.local.toml"`。第三方Key只能发往对应已批准网关。不要把密钥放进聊天、命令行参数、Git或交接文档。

```bash
.venv/bin/review credentials-check --file secrets.local.toml
.venv/bin/review config-check --config config.local.toml
```

这只验证本地配置/权限，不证明Key、模型或服务可用。普通config-check要求HTTPS；如果明确使用HTTP开发网关，应通过显式development预览检查，不能伪造HTTPS地址绕过。HTTP会明文传输源码和凭据。

### 5.3 不联网盘点与模拟演示

```bash

.venv/bin/review -d /path/to/project --source directory --format json

```

Git默认读取已提交HEAD；`--source directory`明确读取工作区当前文件。demo不调用真实模型，不代表真实发现能力。

### 5.4 真实只读审查

```bash
.venv/bin/review --review --development \
  --config /absolute/tool/config.local.toml \
  -d /absolute/target --source head \
  --include package/a.py --include package/b.py \
  --output /absolute/outside/new-review-report
```

第一次仅预览。人工核对范围、endpoint、未知费用和限额后，在**完全相同命令**后追加 `--approve <approval_digest>`。报告目录必须位于目标外且不存在。只读审查一轮最多8次请求，不要把超过32KiB的选择当作自动全仓审查；根据预览分批建议明确选择范围。

### 5.5 Docker测试与自动修复

通用预览：

```bash
.venv/bin/review repair-run --development \
  --config /absolute/tool/config.local.toml \
  -d /absolute/git-target \
  --include package/a.py --include package/b.py \
  --image 'sha256:<本机已准备镜像的64位摘要>' \
  --output /absolute/outside/new-repair-report \
  --max-calls 48 --test-timeout 180 --patch-scheduling grouped
```

- 第一次只预览；核对后同命令追加 `--approve <approval_digest>` 才执行。
- 若只想测试，在预览和批准的两次命令中都添加 `--tests-only`：零模型请求、无补丁、无写回，但仍创建HEAD候选并在Docker测试。
- 默认 `--test-sandbox strict`。只有测试确实需要容器内临时可执行文件且显式接受这一扩大权限时，才使用 `--test-sandbox exec-scratch`；它不是strict的同义选项。
- `--test-timeout`是所有测试组共享的Docker期限，不改变模型worker的60秒期限。
- 审查/修改范围由 `--include` 限定；测试范围是全部可发现且允许导出的已提交测试，不是只测试include文件。
- 通过最终测试和独立终审后，产品才写回原本干净的选定源码。不要并发编辑目标选定文件。

#### 有限传输重试（2026-11-09后续新增）

`repair-run`默认启用`--transport-retries 2`：原请求失败后最多再尝试2次，总共最多3次；等待依次为1秒、2秒。设置`--transport-retries 0`关闭，`1`表示最多重试一次。仅重试`http_status_408`、`response_timeout`、`worker_timeout`；鉴权/参数错误、429、5xx、泛网络错误、TLS/协议错误及响应缺少用量不重试。只读审查及直接DevelopmentConfig默认仍为0；tests-only实际固定为0。

每次实际尝试均重新授权、计入phase和总调用额度，等待后重新检查源码/候选、有效期及剩余额度，不借终审预留。更小的恢复阶段限额优先：证据纠错总共仅1次请求，故该阶段不能传输重试；依赖复核/Reviewer依赖重审总共3次请求，重试消耗同一额度。单次60秒超时不变，因此一个逻辑请求可能等待约183秒，仍受运行授权寿命约束。改变重试配置必须重新预览并批准新摘要，旧审批不可复用。

后续成功仅恢复执行流程：之前失败记录、错误码及未知用量保留，`usage_complete`仍为false、金额仍未知，可能存在重复计费。最终测试/终审门禁不变；含未知用量的报告即使重试恢复也不能作为seed。JSON逐条记录`retry_attempt`、`retry_status`及`recovered_by_call`，call编号在各phase内独立；Markdown区分已恢复与未恢复失败。此改动没有自动重开第19轮，也没有发起第20轮真实付费验收。

#### 显式不设总调用次数上限（2026-11-09后续新增）

用户另行要求一次不受48次上限影响的全流程验收。新参数`--no-call-limit`与`--max-calls`互斥；把上例的`--max-calls 48`替换为`--no-call-limit`，重新预览并批准新摘要，才能使用。默认仍是48次；新模式的`preview.max_calls`为JSON `null`，`no_call_limit=true`，费用未知且可能增加，不代表零费用。

该参数只移除本次运行的**总模型调用次数**限制，不是无限修复或保证成功：每phase8次、每请求60秒、输出2048tokens、源码上下文32768字节、8次成员补丁尝试、4轮refresh、一小时授权期限以及所有最终测试/终审/工作区保护仍保留。没有数值终审预留，但终审流程仍强制执行。当前repair-run对HTTP408及显式超时默认有限重试；未恢复的失败、其他传输错误或响应用量缺失仍停止。重试不豁免这些限制。第19轮执行时尚未加入重试。

当前仅支持从新HEAD候选启动，不与`--tests-only`或`--seed-report`组合。更大调用量报告不承诺能导入旧有界seed机制。一次显式验收不等于授权无限重启。产品与实际验收证据见`docs/superpowers/plans/2026-11-09-uncapped-call-acceptance.md`。
